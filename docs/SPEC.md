## 1. 背景・目的

### 1.1 背景

大学の研究成果（技術シーズ）を産学連携で産業界と接続する活動は、長年にわたって行われているが、依然として「マッチング精度の低さ」「連携後の頓挫」「シーズプッシュ型の失敗」といった構造的問題を抱えている。yet2.com、日本のTLO制度、欧州のオープンイノベーションコミュニティなど、過去のマッチングプラットフォームの大半が「シーズを並べて企業に見せる」アプローチを取り、撤退や形骸化に陥った。

一方、P&G「Connect+Develop」、武田薬品「COCKPI-T」、産総研×ストックマーク「Bibbidi」など、ニーズ起点（バックキャスト型）のアプローチを採用したケースは比較的高い成功率を示している。しかし、これらは「企業が自ら課題を構造化して投稿する」ことを前提としており、日本の大企業の多くが持つ「課題を言語化・公開発信できない」という文化的特性に対応していない。

### 1.2 目的

本システムは、**大学の技術シーズを入力として、大企業の公開情報（IR・有価証券報告書・特許・統合報告書・ニュース等）からバックキャストで潜在ニーズを推定し、産学連携の可能性を仮説として生成する**ことを目的とする。これは既存の商用サービスが提供していない第五のカテゴリー（ベストプラクティス調査レポート §2参照）に位置する独自アプローチである。

最終的なシステムの利用者は、産学連携コーディネーター、大学TLO担当者、コンサルタント（西村自身を含む）であり、彼らが大企業との連携仮説を素早く形成し、実際のアプローチに移るための意思決定支援ツールとして機能する。

### 1.3 解決したい具体的な問題

第一に、産学連携コーディネーターが大学シーズを手にしたとき、「どの大企業に持ち込むべきか」を判断する材料が乏しい。各社のIR・有報・統合報告書を一社ずつ読み込む作業は非現実的であり、結果として「知っている企業」「過去に縁のある企業」に偏ったアプローチになりがちである。

第二に、大企業側のニーズは公開情報に分散しており、人手での横断分析が困難である。中期計画には抽象的な戦略しか書かれず、具体的な技術ニーズはR&D部門の頭の中にしか存在しない。これを公開情報から推定する技術的手段が必要である。

第三に、マッチングの根拠を説明できないと、コーディネーターも企業側もシステムを信頼しない。「なぜこの企業なのか」を明示する説明可能性（Explainable AI）が不可欠である。

## 2. スコープ

### 2.1 対象範囲（やること）

本システムの第一バージョン（v1.0）は以下を実装する。

**入力**: 大学技術シーズの記述（テキスト、論文DOI、特許番号のいずれか、または複数）

**処理**: 入力シーズに対して、対象企業群（東証プライム上場の研究開発費上位500社）から連携可能性の高い候補をスコアリングし、上位10〜20社を抽出する。各候補について、なぜ適合するかの根拠（技術的近接性、吸収能力、推定された潜在ニーズとの一致点、過去の連携実績）を説明テキストとして出力する。

**出力**: マッチング候補リスト（企業名・スコア・根拠説明・推奨連携モード）をMarkdownレポート形式およびJSON形式で提供する。

**情報源**: EDINET API（有報・統合報告書）、J-PlatPat API（特許）、Semantic Scholar API（学術論文）、Claude API（バックキャスト推定）。

### 2.2 対象外範囲（やらないこと）

以下は本バージョンでは対象外とする。明示することで、後の「やはりやってほしい」という追加を防ぐ。

- 企業側ユーザー向けのインターフェース（本システムは大学・コーディネーター側のツール）
- 中小企業・非上場企業のカバー（情報源が公開情報に限定されるため）
- 海外大学・海外企業のマッチング
- 連携契約のドラフト作成、IP交渉支援
- リアルタイムマッチング（バッチ処理で十分）
- マッチング候補との直接コンタクト機能（メール送信等）
- 機械学習による重み学習（v1.0では固定重み、v2.0以降で対応）
- TRL自動推定（v2.0以降）
- 求人情報・プレスリリースの統合（v2.0以降）

### 2.3 既存資産との関係

先日構築した **IR Collector**（`~/projects/apps/ir-collector/`、GitHub: yuyanishimura0312/ir-collector）が、EDINET API クライアントとSQLiteメタデータ管理機能を完成させている。本プロジェクトはこれをデータ取得層として再利用する。IR Collectorで収集された有報PDF・XBRLおよびメタデータDBを、本システムが読み取り・解析する形で連携する。

## 3. ユーザーストーリー

### 3.1 主要ペルソナ

**ペルソナA: 産学連携コーディネーター（西村自身）**
ミラツクのコンサルタントとして、特定の大学研究者からシーズの相談を受け、それを最適な大企業に持ち込む役割を担う。月に5〜10件程度のシーズ相談があり、各案件で「どの企業に持ち込むか」の選定に時間を取られている。

**ペルソナB: 大学TLO担当者**
特定大学の技術移転オフィスに所属し、大学内の研究シーズを企業に売り込む役割を持つ。リサーチャー数十名を抱えるが、企業側情報を体系的に把握する手段を持たず、過去の取引先や知人ベースでアプローチしているのが実情。

### 3.2 ユーザーストーリー

**US-1**: 「大学技術シーズ A 件があるとき、コーディネーターとして、5分以内にトップ10の連携候補企業リストとその根拠を得たい。それにより1日かけていた候補企業の選定作業を10分に短縮できる」

**US-2**: 「コーディネーターとして、各候補企業について『なぜこの企業が候補か』の根拠を3つ以上の観点（技術的適合・吸収能力・潜在ニーズの一致点・過去の連携実績のいずれか）から確認したい。それによりクライアント大学に対して説明責任を果たせる」

**US-3**: 「コーディネーターとして、自分の知っている企業もリストに含まれているか、含まれていない場合はなぜスコアが低いのかを確認したい。それによりシステムの判断と自分の経験的判断を照合し、システムの信頼性を評価できる」

**US-4**: 「TLO担当者として、複数のシーズをバッチ的に処理したい。月初に20件のシーズを一括投入し、各シーズに対するマッチング候補を朝までに得られればよい」

**US-5**: 「コーディネーターとして、出力結果に対して『この候補は外して』『この観点をもっと重視して』といったフィードバックを与え、次回以降の精度を向上させたい（v2.0以降）」

### 3.3 利用シナリオ例

ある大学の材料科学研究者から「自己組織化ハニカム構造を持つ多孔質フィルム」という技術シーズの相談があったとする。コーディネーターは本システムにシーズの説明文と関連論文DOIを入力する。システムは数分以内に以下を出力する。

トップ10候補として、富士フイルム、日東電工、三菱ケミカル、東レ、ニプロ、テルモ、JSR、信越化学、住友ベークライト、ダイセルが提示される。各社について、技術的近接性スコア（特許IPC分布の類似度）、吸収能力スコア（R&D集約度、研究員数）、潜在ニーズの一致点（中期計画から推定された技術領域とシーズのマッチ）、過去の連携実績（共同特許・共著論文の有無）が表形式と説明文で提示される。

特に富士フイルムについては、「東北大学下村研究室との既存の共同特許がある」「Open Innovation Hubでハニカムフィルム関連のキーワードに反応した過去事例あり」「中期計画ヘルスケア領域でのバイオマテリアル探索方針と整合」といった根拠が示される。コーディネーターはこの情報をもとに、富士フイルムの該当部署へのアプローチ戦略を組み立てる。

## 4. 機能要件

### 4.1 必須機能（v1.0）

#### F-1: 大学シーズ入力モジュール
- ユーザーは大学シーズを以下のいずれかの形式で入力できる
  - 自由記述テキスト（200〜2000字）
  - 論文DOIまたはSemantic Scholar ID
  - 特許番号（J-PlatPat形式）
  - 上記の組み合わせ
- 入力されたシーズは内部的に統一フォーマットに変換され、後続の処理で使われる
- 入力シーズの「技術領域ベクトル」（IPCコードまたはセマンティックエンベディング）が抽出される

#### F-2: 企業データベース管理
- 対象企業（東証プライム上場かつ研究開発費上位500社）のメタデータをSQLiteで管理
- 各企業について以下の情報を保持
  - 識別情報（企業名、EDINETコード、証券コード、業種）
  - 財務基礎（売上高、営業利益、時価総額）
  - R&D投資（研究開発費、対売上高比率）
  - R&D活動テキスト（有報[研究開発活動]セクション全文）
  - 中期計画の重点領域（IR・統合報告書から抽出）
  - 特許ポートフォリオ（過去5年のIPC分布、出願件数）
  - 共同出願実績（大学との共同特許）
- 月次バッチで自動更新される

#### F-3: 連携可能性スコアリング
- 入力シーズと各企業のペアに対してスコアを計算
- スコア式: `Score(s,c) = 0.20·TechProx + 0.20·AbsCap + 0.30·NeedFit + 0.10·PastTies + 0.10·TRLCompat + 0.10·OpenInnoMaturity`
- 各特徴量の定義は §5.1 を参照
- スコアは0〜1の範囲に正規化

#### F-4: バックキャスト型ニーズ推定
- 各企業のR&D活動テキスト・中期計画テキストをClaude APIに渡し、潜在ニーズ（その企業が今後3〜5年で必要とする可能性が高い技術領域）を推定
- 推定結果はテキストおよびエンベディングとしてキャッシュ
- 推定の根拠（どのテキスト箇所から推定したか）も保持
- 月次で再生成

#### F-5: マッチング結果出力
- スコア上位N社（デフォルト10社）をリスト化
- 各候補について以下を出力
  - 企業名・基本情報
  - 総合スコアおよび各特徴量別スコア
  - 根拠説明（テキスト3〜5文）
  - 推奨連携モード（共同研究 / ライセンス / 受託開発 / 中長期研究契約 のいずれか）
- 出力形式は Markdown と JSON の両方
- 結果はファイルに保存（後で参照可能）

#### F-6: バッチ処理
- 複数のシーズを一括で処理できるCLIコマンドを提供
- 入力ディレクトリに置かれたシーズファイル（.md または .json）を順次処理
- 結果を出力ディレクトリに書き出す

### 4.2 推奨機能（v1.5）

- F-7: 結果のWeb閲覧UI（FastAPIベースのシンプルなWebダッシュボード）
- F-8: マッチング結果の差分比較（同じシーズを再実行したときの変化を可視化）
- F-9: 業種フィルタ（特定業種に絞ったマッチング）

### 4.3 将来機能（v2.0以降）

- F-10: ユーザーフィードバックに基づく重み学習
- F-11: 求人情報・プレスリリースの統合
- F-12: TRL自動推定
- F-13: 大学・研究室・研究者単位での候補企業推薦
- F-14: 中小企業・非上場企業の対応

## 5. データモデルとロジック

### 5.1 連携可能性スコアの定義

#### TechProx(s, c) — 技術的近接性
大学シーズ s の技術領域ベクトルと企業 c の特許ポートフォリオベクトルのコサイン類似度を計算し、Petruzzelli (2011) の逆U字型関係に従って評価関数 `f(x) = 4x(1-x)` で変換する。

実装は2段階。第一段階ではIPCコード4桁分布のコサイン類似度を計算する高速版を使う。第二段階（v1.5以降）でSentence-BERTによるセマンティック類似度に置き換える。

#### AbsCap(c) — 吸収能力
以下の3指標を業種別に標準化し、対数変換を施した上で平均する。
- R&D集約度: 研究開発費 ÷ 売上高（業種別に正規化）
- R&D絶対額: 研究開発費の対数値
- 特許出願密度: 過去5年の出願件数 ÷ 従業員数

業種別正規化は、製薬・電機セクターへの過度な偏りを防ぐために必須。

#### NeedFit(s, c) — ニーズ適合度
本システムの中核。Claude APIで企業 c の中期計画・統合報告書から推定された潜在ニーズの記述を、シーズ s が解決しうる事業課題の記述と意味的に比較する。比較はSentence-BERTのコサイン類似度で行う。

潜在ニーズの推定は月次バッチで事前計算し、キャッシュする。シーズとの照合は実行時に行う。

#### PastTies(s, c) — 過去の連携実績
以下を集計し、対数変換した値を使う。
- 大学（または同分野の大学群）と企業 c の共同特許出願数（過去10年）
- 共著論文数（過去10年、Semantic Scholarから取得）
- ただし「過去実績ゼロ」を強くペナルティしない（重みw4=0.10に抑制）

#### TRLCompat(s, c) — TRL適合性
シーズと企業ニーズのTRLギャップを推定し、以下の閾値関数を適用。
- ギャップ ≤ 3: 1.0
- ギャップ 3〜5: 0.7
- ギャップ > 5: 0.4

v1.0ではTRLは粗い推定（論文ベース=TRL2、特許ベース=TRL4、商用化済=TRL7のような単純ルール）で十分とする。

#### OpenInnoMaturity(c) — オープンイノベーション成熟度
以下のチェック項目をスコア化（各項目1点、最大5点を1.0に正規化）。
- CVC設立有無
- オープンイノベーション専担組織の有無
- 過去5年のCEO/CTOのオープンイノベーション関連発言の有無
- 過去5年のスタートアップ連携実績の有無
- 過去5年の大学連携実績の有無

NIH症候群フィルターとして機能する。情報源は統合報告書・プレスリリース・各社サイトのスクレイピング。v1.0では一部を手動入力で補完してよい。

## 6. 非機能要件

### 6.1 性能
- 1シーズあたりのマッチング処理時間: 5分以内（500社対象）
- バッチ処理: 20シーズを夜間（8時間以内）で完了
- バックキャスト推定の月次バッチ: 500社を24時間以内で完了

### 6.2 信頼性
- 外部API（EDINET、J-PlatPat、Semantic Scholar、Claude）の障害時はリトライ＋スキップで継続
- 部分的なデータ欠損があってもマッチングは継続実行（欠損特徴量は中央値で補完）

### 6.3 セキュリティ
- APIキー（EDINET、Anthropic等）は `.env` で管理しgit除外
- 企業情報はすべて公開情報のみを扱う（非公開情報は一切扱わない）
- ユーザー入力のシーズ情報はローカルに保存し、外部送信しない（Claude APIへの送信を除く）

### 6.4 説明可能性
- すべてのマッチング結果に「なぜこのスコアか」の根拠を添える
- ブラックボックス化を避ける。スコアの内訳と各特徴量の計算根拠が追跡できる
- LLM出力（バックキャスト推定）は「これは推定であり仮説である」と明示する

### 6.5 拡張性
- 特徴量の追加・削除がコード変更なしで（設定ファイルで）可能な設計
- 新しい情報源（求人・プレスリリース等）の追加が容易な構造

### 6.6 法的・倫理的
- 公開情報のみを使用し、個人情報・機密情報を扱わない
- 特定企業を不利に扱う出力は行わない（ネガティブな評価ではなく「スコアが低い」という表現に留める）
- 出力は「仮説」であり最終判断はユーザーに委ねることを明示

## 7. 技術スタック

### 7.1 言語・フレームワーク
- **Python 3.11+**: メインの実装言語
- **SQLite 3**: メタデータDB（後にPostgreSQLへの移行も検討）
- **Sentence-Transformers**: セマンティックエンベディング（intfloat/multilingual-e5-small または同等）
- **FastAPI**: Web UI（v1.5以降）
- **Click**: CLIフレームワーク

### 7.2 外部API・データソース

| サービス | 用途 | 認証 | コスト |
|---|---|---|---|
| EDINET API v2 | 有報取得 | Subscription Key（無料） | 無料 |
| J-PlatPat | 特許検索 | Webスクレイピング or API | 無料（要注意） |
| Semantic Scholar API | 論文・引用情報 | API Key（無料） | 無料 |
| Claude API (Anthropic) | バックキャスト推定 | API Key | 従量課金 |
| 統合報告書 | 中期計画テキスト | 各社サイトから取得 | 無料 |

J-PlatPatの利用は規約を確認の上、過度なリクエストを避ける。代替として GBI（特許情報研究所）等の有料DBの利用も将来的に検討。

### 7.3 既存資産の再利用

- **IR Collector** (`~/projects/apps/ir-collector/`): EDINET API クライアント・SQLite基盤・収集スクリプトを依存ライブラリとして利用
- 必要に応じてIR Collectorに機能追加（共有関心領域）

### 7.4 推定コスト（Claude API）

- バックキャスト推定: 1企業あたり約 5,000 入力トークン + 1,000 出力トークン
- 500社 × 月1回 = 2,500,000 入力 + 500,000 出力 トークン/月
- Sonnet使用時: 約 $7.5 + $7.5 = **約$15/月**
- マッチング時のシーズ解釈: 1シーズあたり約 2,000 トークン
- 月20シーズなら追加で約$1未満

## 8. 段階的実装ロードマップ

### Phase 1: MVP（3か月想定）

**ゴール**: 単一シーズに対して10候補企業を出力するCLIツールを完成させる。

**実装内容**:
- IR Collectorを基盤としたデータ取得層の構築
- 対象500社のメタデータ収集（手動シードリストから開始）

- 出力: Markdownレポート

**完了条件**:
- 5件のテストシーズに対してマッチング結果が出力される
- 出力結果に対して西村本人がレビューし、「妥当な候補が含まれている」と評価する
- 全テストで処理時間5分以内

### Phase 2: バックキャスト統合（6か月想定）

**ゴール**: NeedFit特徴量を実装し、本システム独自の差別化機能を完成させる。

**実装内容**:
- Claude APIでの潜在ニーズ推定モジュール
- 推定結果のキャッシュとエンベディング
- スコア式に NeedFit を統合（推奨重み: 0.30）
- 推定根拠の出力強化
- バッチ処理コマンドの実装

**完了条件**:
- 10件のシーズに対して、Phase 1と比較して上位候補が変化していること
- 変化が「より妥当」であることを西村本人と外部のコーディネーター1名が評価

### Phase 3: 高度化（12か月想定）

**ゴール**: TRL推定、オープンイノベーション成熟度、説明可能性の強化。

**実装内容**:
- TRLCompat・OpenInnoMaturity の実装
- 統合報告書・プレスリリースのスクレイピング
- Web UI（FastAPIベース）
- ユーザーフィードバック収集

### Phase 4: 拡張（v2.0以降）

- ユーザーフィードバックに基づく重み学習
- 中小企業対応
- 大学・研究室・研究者単位の推薦

## 9. 完了の定義（Definition of Done）

各Phaseの完了は以下の条件を満たすこととする。

**コード品質**: すべての関数に型ヒントが付与されている。主要なクラス・関数にdocstringが付いている。SAST（bandit等）でクリティカルな指摘がない。

**テスト**: 主要なロジック（スコアリング、データ取得）に対してユニットテストが存在し、すべてパスする。エンドツーエンドのスモークテストが1つ以上存在する。

**ドキュメント**: README.md にインストール手順・使い方・アーキテクチャ図が記載されている。`docs/` 配下に主要なAPIリファレンスがある。

**バージョン管理**: GitHubにプライベートリポジトリとして保存され、各Phaseのリリースタグが付いている。

**動作確認**: 西村本人が手元で実行し、期待される出力が得られることを確認する。

## 10. リスクと対策

### R-1: J-PlatPatのAPI制約・規約問題
**リスク**: J-PlatPatは公式APIが限定的で、スクレイピングは規約上グレー。過度なアクセスでブロックされる可能性。
**対策**: 月次バッチで取得頻度を抑える。代替として特許庁の「特許情報標準データ」の一括ダウンロードを利用する。それでも難しい場合は有料DB（GBI、PatSnap等）を検討。

### R-2: バックキャスト推定の精度
**リスク**: Claude APIによる潜在ニーズ推定が幻覚を含み、誤った仮説を生成する可能性。
**対策**: 出力に必ず「これは推定であり仮説」と明示。複数候補を提示。根拠となるテキスト箇所を引用。Phase 2の完了条件に「人手評価で妥当性確認」を含める。

### R-3: NIH症候群を持つ企業への誤判定
**リスク**: 数値上は高スコアでも経営層レベルでオープンイノベーションを拒否する企業を上位に出してしまう。
**対策**: OpenInnoMaturity特徴量で補正。Phase 1ではこの特徴量がないため、出力結果の解釈に注意することを明記。

### R-4: 競合の出現（産総研Bibbidi等）
**リスク**: AIST Solutionsの「Bibbidi」が機能拡張し、本システムと正面から競合する可能性。
**対策**: 半年ごとに動向をレビュー。Bibbidiは産総研シーズに限定されているため、本システムは「全大学シーズ + バックキャスト推定」での差別化を維持する。

### R-5: 法的・倫理的問題
**リスク**: 「企業の公開情報を集約して潜在ニーズを推定する」行為が、特定企業から見て侵襲的・攻撃的と受け取られる可能性。
**対策**: 出力は仮説と明示。商用提供時には法務レビューを必須とする。当面は西村個人およびミラツク内部での使用に限定する。

### R-6: データ更新の継続性
**リスク**: 月次バッチが運用負荷で停止し、データが古くなる。
**対策**: cron＋ログ監視で自動化。失敗時の通知をSlackに連携。

## 12. 用語集

- **TTO**: Technology Transfer Office、大学技術移転オフィス
- **TRL**: Technology Readiness Level、技術成熟度レベル（NASA定義の1〜9段階）
- **吸収能力 (Absorptive Capacity)**: 企業が外部知識を認識・同化・活用する能力（Cohen & Levinthal 1990）
- **R&D集約度**: 研究開発費 ÷ 売上高
- **NIH症候群**: Not Invented Here、外部由来の技術を拒否する組織文化
- **CVC**: Corporate Venture Capital、企業内ベンチャー投資組織
- **バックキャスト**: 望ましい未来から逆算して現在の戦略を導く思考法
- **IPC**: International Patent Classification、国際特許分類
- **NeedFit**: 本システム独自の特徴量。推定された潜在ニーズとシーズの適合度
